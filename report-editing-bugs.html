היקף: יצירה, עריכה, מחיקה, שמירה, טעינה מחדש, ניווט והרשאות של רשומות נמענים.

תקציר מנהלים

נמצאו שישה באגים פעילים בזרימת העריכה. שניים מהם קריטיים: ה־API אינו מאמת זהות משתמשת, וכל מי שמכיר מספר טלפון ו־hashCode יכול לקרוא או לשנות נתונים; וכן משתמשת יכולה לדרוס נמען של משתמשת אחרת. שלושה באגים נוספים עלולים לגרום לאובדן עריכה או מחיקה שטרם נשמרו. הממצא השישי הוא ממשק API מת שנותן 404 אם ייעשה בו שימוש.

חומרהכמותמשמעות
קריטית2חשיפת מידע או שינוי מידע של משתמשות אחרות.
גבוהה3אובדן עריכות או מחיקות שהמשתמשת ציפתה שישמרו.
בינונית1נקודת כשל בנתיב API שאינו מחובר למסך הפעיל.

זרימת הנתונים הקיימת

הקלדה בתא / פעולה בטבלה
        ↓
DataTable.rows (state פנימי)
        ↓ onAutoSave, רק בפעולות שקוראות לו
Dashboard.records + localStorage[records-{phone}] + isTableDirty=true
        ↓ לחיצה על “שמור את כל המוזמנים”
POST /api/recipients/save { phone, recipients, hashCodesToDelete }
        ↓
RecipientController → recipients + user_recipients
        ↓
תגובה → Dashboard.setRecords(finalRecords) + localStorage

בכניסה מחדש לדשבורד, loadRecords מבצע GET /api/recipients?phone=…. אם השרת מחזיר לפחות שורה אחת, גרסת השרת מחליפה את המצב המקומי; הגיבוי המקומי נקרא רק כאשר התשובה ריקה או שהבקשה נכשלת.

ממצאים מפורטים

1. אין אימות זהות ב־API קריטית

הבעיה: אין Session בצד השרת, JWT או מנגנון הרשאה אחר. הלקוח שומר את אובייקט המשתמש ב־sessionStorage ושולח מספר טלפון כפרמטר או בגוף הבקשה. השרת משתמש במספר זה כדי לבחור משתמשת.

GET /api/recipients?phone=050… → findByPhone(phone) → מחזיר נמענים
POST /api/recipients/save { phone: "050…", ... } → findByPhone(phone) → שומר

השפעה: לקוחה יכולה לשנות את ה־phone בבקשת דפדפן ולקרוא, למחוק קישור או לשמור רשומות בשם משתמשת אחרת. מספר טלפון אינו אישור זהות.

ראיות: AuthController.java:22–35 מחזיר אובייקט משתמש בלבד; RecipientController.java:73, 215–224, 337–341 מקבל ומאמין ל־phone מהבקשה; אין שכבת Spring Security בפרויקט.

תיקון: להוסיף אימות שרת־צד; להפיק token בהתחברות; להסיק את המשתמשת מתוך ה־token בכל endpoint; לא לקבל phone כאמצעי הרשאה.

2. עדכון עם hashCode של משתמשת אחרת דורס את הנמען שלה קריטית

הבעיה: בכל שורה שיש בה hashCode, השרת מכניס אותה ל־existingRows וקורא ל־recipientRepository.saveAll, בלי לבדוק שיש קישור בין הנמען למשתמשת המבצעת.

משתמשת ב' שולחת hashCode של נמען של א'
  → existingRows
  → saveAll(existingRows)
  → UPDATE recipients
  → תוכן הנמען של א' מוחלף

הוכחה: קיימת בדיקת אינטגרציה בשם save_existingHashCode_updatesRegardlessOfWhichUserSentIt ב־RecipientControllerTest.java:228–253. ההערה בבדיקה עצמה מגדירה זאת “פער אבטחה ידוע”, והבדיקה מאשרת שהדריסה מצליחה.

תיקון: לפני עדכון כל hashCode, לוודא שקיים user_recipients עבור המשתמשת המאומתת והנמען. בהיעדר קישור להחזיר 403 ולא לבצע saveAll.

3. עריכה מקומית נעלמת ברענון או במעבר למסך אחר גבוהה

הבעיה: הקלדה נשמרת מקומית, אך אין סימון מתמשך שמבדיל בין צילום מצב שנשמר בשרת לבין טיוטה מקומית. לאחר unmount של הדשבורד, loadRecords מעדיף את השרת בכל מצב שבו הוא מחזיר רשימה לא ריקה.

הקלדה → localStorage מכיל גרסה חדשה
ניווט להגדרות / תצוגה מקדימה / רענון
→ Dashboard נטען מחדש → GET לשרת
→ השרת מחזיר גרסה ישנה אך לא ריקה
→ setRecords(response.data)
→ הטיוטה המקומית אינה מוצגת

מסלולי הניווט: DashboardPage מנווט ל־/settings; PrintModal מנווט ל־/print-preview. שניהם מחליפים route ולכן הדשבורד נבנה מחדש.

ראיות: DashboardPage.jsx:65–91 ו־:170–175; ה־fallback ל־localStorage קורה רק בתשובה ריקה או catch.

תיקון: לשמור מעטפת טיוטה עם dirty, זמן שינוי וגרסת שרת אחרונה. בטעינה: אם יש טיוטה dirty, להציע שחזור או להעדיף אותה באופן מפורש. להוסיף guard לניווט פנימי וליציאה.

4. שורה חדשה ללא הקלדה אינה נשמרת בגיבוי המקומי גבוהה

הבעיה: כפתור “הוסף שורה” וכן פעולת הוספה לפני/אחרי שורה משנים רק את rows בתוך DataTable. הם אינם קוראים ל־onAutoSave.

הוסף שורה → setRows בלבד
אין כתיבה ל-localStorage
אין isTableDirty=true
רענון / ניווט → השורה נעלמת

ראיות: DataTable.jsx:557–566 ו־:571–580. לעומת מחיקה ועריכת תא, שקוראות ל־onAutoSave.

תיקון: לחשב את המערך החדש בתוך callback, לעדכן אותו ב־setRows ולקרוא באותה פעולה ל־onAutoSave(nextRows). יש לכסות גם “הוסף לפני” ו“הוסף אחרי”.

5. מחיקה שממתינה לשמירה אובדת ברענון או בניווט גבוהה

הבעיה: השורה אכן מוסרת מהטבלה ומה־localStorage, אבל רשימת ה־hashCode שיש למחוק בשרת נשמרת רק ב־React state בשם pendingDeleteHashCodes. היא אינה נכתבת לאחסון מתמשך.

מחק שורה שמורה → הטבלה המקומית אינה מציגה אותה
pendingDeleteHashCodes=[hash] בזיכרון בלבד
רענון / מעבר למסך → state מתאפס
GET מהשרת מחזיר שוב את השורה
→ המחיקה לא נשלחת לעולם

ראיות: DashboardPage.jsx:181–190 מגדיר useState([]); אין קריאה ל־localStorage עבור רשימת המחיקות. handleSave שולח את הרשימה רק אם הדשבורד עדיין חי.

תיקון: לשמור את תור המחיקות ב־localStorage לפי משתמשת, לטעון אותו בתחילת הדשבורד, ולהסיר ממנו רק אחרי תשובת שמירה מוצלחת.

6. עריכה בזמן שבקשת שמירה פתוחה יכולה להידרס גבוהה

הבעיה: handleSave שולח צילום מצב של updatedRows. בזמן שהבקשה מחכה לתשובה המשתמשת עדיין יכולה להקליד. כשהתגובה חוזרת, הקוד קורא ל־setRecords(finalRecords) מתוך הצילום הישן ומסמן isTableDirty=false.

לחיצה על שמור: snapshot A נשלח
המשתמשת משנה תא: state/localStorage = B
תגובה ל-A מגיעה: setRecords(finalRecords של A)
→ B נדרס; הדגל מציג שהטבלה נקייה

ראיות: DashboardPage.jsx:195–272. אין נעילת עריכה, מספר גרסה או בדיקה שה־state השתנה במהלך הבקשה.

תיקון: לנעול את פעולת העריכה בזמן save, או לנהל revision מקומי: לנקות dirty ולהחליף state רק אם revision התגובה זהה ל־revision שנשלח. אחרת לשמור את השינוי החדש כטיוטה ולהציג “יש שינויים שטרם נשמרו”.

7. נתיב upload-excel מוגדר בלקוח אך אינו קיים בשרת בינונית

הבעיה: הלקוח מגדיר POST /recipients/upload-excel, אך ב־RecipientController אין endpoint כזה. ה־imports של MultipartFile ו־ExcelService קיימים אך אין שימוש.

השפעה: כל קוד שיקרא ל־api.uploadExcel יקבל 404. הייבוא הפעיל כיום מעבד Excel בדפדפן, לכן אין פגיעה במסלול הפעיל כרגע.

תיקון: להסיר את לקוח ה־API המת, או לממש endpoint תואם עם אימות והרשאה.

ממצאים שנבדקו ואינם באג פעיל בענף זה

  • אטומיות שמירה ומחיקה: saveRecipients מסומן @Transactional, לכן הממצא הישן של עדכון חלקי בעקבות כשל באמצע אינו תקף בענף זה.
  • מחיקה בלבד: recipients יכול להיות null ללא NullPointerException; קיימת בדיקה המכסה את התרחיש.
  • hash חדש לשתי כפילויות שהוחלט להשאיר: קיימת בדיקה ל־duplicateSalt, והיא מכסה החזרת מזהים שונים.

סדר תיקון מומלץ

  1. להוסיף אימות והרשאות שרת־צד ולחסום עדכון/קריאה לפי phone מהלקוח.
  2. לבדוק בעלות על כל recipient לפני עדכון, מחיקה או קריאת היסטוריה.
  3. להפוך טיוטה מקומית ומחיקות ממתינות למצב מתמשך עם חיווי ברור למשתמשת.
  4. לפתור מרוץ בין עריכה לשמירה באמצעות revision או נעילת טבלה זמנית.
  5. לחבר כל פעולת הוספת שורה ל־onAutoSave.
  6. להסיר או לממש את נתיב upload-excel.

אימות הבדיקה ומגבלות

בוצעה סקירת קוד סטטית של מסלולי ה־frontend וה־backend, כולל בדיקות האינטגרציה הקיימות. בדיקת ה־backend לא הורצה במכונה זו: הפקודה mvn test נכשלה לפני התחלה כי Maven ו־Java אינם זמינים ב־PATH. בניית ה־frontend הופעלה באמצעות npm.cmd run build; בזמן יצירת הדוח תהליך הבנייה עדיין רץ ולא החזיר תוצאת הצלחה או כשל, ולכן אין לייחס לדוח תוצאת build.
